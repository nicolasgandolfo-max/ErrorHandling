Phase 3 Exp. 4 — terminal decision, and the catch-all
E4 Final decision

We couldn't complete this payment

Nothing was charged. Our team on WhatsApp can look into it with you.

Reference 8F3K-2201
Message us on WhatsApp Done
Notes
  • No reason, no retry, no method switch, no amount edit. Support is the only forward path.
  • Also the fallback for any unmapped decline code and for a capability timeout.
  • The reference is a support lookup key only — it must not encode the decline reason, and agents see the reason, the user never does.
  • No warning colour and no siren illustration: a terminal state read as an error invites retries the system won't honour.
  • The same screen serves E3 cancel/failure. One design, four entry points.
Rules the copy follows
  • Never names what the payment was for. No "transfer", "remittance", "top-up", "loan", no recipient country, no product name.
  • Says what happened to the money before saying what to do — "nothing was charged" comes first.
  • One primary action per screen, and it's always the path the system actually wants.
  • Sentence case throughout. No exclamation marks, no apology theatre, no emoji.
  • The failed instrument is described by its state ("unavailable"), never by its diagnosis ("reported stolen").
  • Turquoise carries the recovery action; orange appears only on a field-level error, never as the mood of a screen.
Open questions
  • Step-up mechanism for Exp. 3 — blocks the E3-B host design.
  • Whether L2 can run in-line — blocks E6-B, and changes E6-A's primary action.
  • Compliance on showing the available limit — decides whether E5-B ships.
  • Degraded behaviour when the capability is down — currently proposed as E4 after 8 s.
  • Retry counter reset rule for E1-B.
